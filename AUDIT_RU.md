## 0. Кратко (TL;DR)

**Что хорошо.** Ядро правил — чистые функции без побочных эффектов, покрытые тестами; сохранения валидируются fail-closed; RNG детерминированный; есть документация решений (ADR) и честные отчёты о том, что проверено, а что нет.

**Главные проблемы.**

| # | Проблема | Тип | Серьёзность |
|---|---|---|---|
| L1 | Рекламный бонус после честного GMI ≥ 75 (+25 % к аудитории) **никогда не заканчивается по времени** — константа `GMI_AD_BOOST_HOURS = 72` фактически не работает | логика | высокая |
| L2 | «Серый» контракт даёт ×1.8 денег и **не несёт никакого риска**, хотя UI обещает обратное — чистый эксплойт | логика/баланс | высокая |
| L3 | Найм сотрудника списывает деньги, но **не пишет в бухгалтерию** (`totalExpenses`/`totalCapex`) — экран «Финансы» врёт | логика | средняя |
| L4 | **Три разных формулы игрового дня** (экономика, сезонность, UE-тулбар) → в UE день на панели расходится с днём в контрактах/бенчмарках | логика | средняя |
| L5 | Старый результат бенчмарка **никогда не устаревает**: GMI дня 5 сравнивается с конкурентом и в день 300 | дизайн | средняя |
| U1 | В UE включены **Lumen GI + Lumen Reflections + Virtual Shadow Maps + Distance Fields** для города из non-Nanite HISM-мешей — самая дорогая связка рендеринга для сцены, которой это не нужно (50 % GPU RTX 3090 на 900p) | оптимизация | высокая |

## 1. Что это за проект и как он устроен

### 1.1 Две игры на одном ядре

```
┌─────────────────────────────── src/systems ────────────────────────────────┐
│ Чистые правила: экономика, рынок, обучение, контракты, события, закупки,     │
│ портфель моделей (models/*), сохранения V0–V3 (persistence/*)              │
└──────────────┬─────────────────────────────────────────────┬───────────────┘
               │                                             │
   ┌───────────▼───────────┐                   ┌─────────────▼──────────────┐
   │ Браузер (Vite+React)  │                   │ Unreal Engine 5.8 (C++)     │
   │ store/gameStore.ts    │                   │ Unreal/Rules/kernel.ts →    │
   │ ui/*.tsx (React)      │                   │   бандл mai-rules.js        │
   │ render/*.ts (three.js)│                   │ MaiRulesVM (QuickJS)        │
   │ IndexedDB             │                   │ MaiRulesSubsystem (JSON ↔)  │
   └───────────────────────┘                   │ mai::Campaign (C++ расшир.: │
                                               │   ревью данных, концовки)   │
                                               │ mai::Simulation (C++ зеркало│
                                               │   экономики, перезаписыв.)  │
                                               │ UMaiNativeWidget (UI из JSON│
                                               │   view-модели Rules/view.ts)│
                                               │ CityV4 (Blender → HISM)     │
                                               └────────────────────────────┘
```

Ключевая идея порта: **UE не переписывает правила на C++, а исполняет тот же TypeScript** внутри QuickJS. Это гарантирует паритет чисел, но приносит цену: каждое действие и каждый тик — сериализация JSON туда-обратно, а поверх ещё живёт C++ «кампания» (ревью датасетов, сложности, концовки), которую нужно синхронизировать с JS-состоянием (`MaiRulesSubsystem::Project`).

## 3. Логические ошибки

### L1. Рекламный бонус GMI не истекает — высокая

`src/systems/market.ts:128`

```ts
const gmiBoost = state.benchmark.adBoostUntil !== null ? 1 + GMI_AD_BOOST : 1
```

Сравнения с `state.elapsedGameHours` нет. `adBoostUntil` выставляется в `benchmark.ts:74` и сбрасывается только при разоблачении накрутки или смене квантования. Итог: один честный тест на 75+ даёт **вечные +25 % к ёмкости аудитории**. Константа `GMI_AD_BOOST_HOURS` фактически мёртвая.

Исправление:

```ts
const gmiBoost = state.benchmark.adBoostUntil !== null && state.elapsedGameHours < state.benchmark.adBoostUntil
  ? 1 + GMI_AD_BOOST : 1
```

Также стоит либо обнулять `adBoostUntil` в `processCompanyDay` после истечения, либо показывать в UI таймер бонуса. Добавить тест «через 73 ч ёмкость вернулась».

### L2. «Серый» контракт без риска — высокая (эксплойт баланса)

`src/systems/contracts.ts:128` ставит `market.dirtyRiskUntil`, но это поле читается **только** в `closeCompletedContract` (`contracts.ts:49-50`) как задержка закрытия. Ни `dailyCourtRoll`, ни `dailyComplaintRoll`, ни `dailyRandomEvent` его не учитывают. При этом текст в `App.tsx:126`: «Через несколько дней после подписи чаще случаются негативные события» — неправда.

Оптимальная стратегия игрока: всегда брать серый (108 000 $ против 60 000 $), риск — ноль.

Исправление (пример): в `events.ts`

```ts
function greyRiskMult(state: GameState) {
  return state.market.dirtyRiskUntil !== null && state.elapsedGameHours < state.market.dirtyRiskUntil ? 2 : 1
}
// dailyRandomEvent: if (rng() >= RANDOM_EVENT_DAILY_CHANCE * greyRiskMult(state)) return state
// dailyCourtRoll:   считать dirtyHistory || серый активен; COURT_DAILY_CHANCE * regionRisk * greyRiskMult
```

Плюс небольшой удар по репутации при подписи серого (−3..−5) — иначе «серый» останется доминирующим выбором.

### L3. Найм не попадает в бухгалтерию — средняя

`src/systems/team.ts:24-35`: `cash −= HIRE_COST`, но `totalExpenses`/`totalCapex` не меняются. Инвариант `cash = START + revenue − expenses − capex` ломается, экран «Как идут дела» показывает неверные суммы. То же самое у прямого `buyDataLot` (`training.ts:33-47`) — в V3 это обёрнуто в `buyModelData` (`models/commands.ts:98-107`), а в ADR (`docs/MODEL_ARCHITECTURE.md`, §10) недостаток признан «тикетом №1». Для найма такой обёртки нет.

Исправление: в `hireEmployee` добавить `totalExpenses: state.totalExpenses + cost` (или `totalCapex`, если считать найм инвестицией — выбрать одно правило и записать в ADR). Добавить тест-инвариант на бухгалтерию после каждого действия из `models/commands.ts` (по аналогии с `audit.test.ts`).

### L4. Три формулы «какой сейчас день» — средняя

| Где | Формула | Когда меняется день |
|---|---|---|
| `market.ts:64` `gameDay()` — контракты, бенчмарк, инвесторы | `floor((h+8)/24)+1` | в полночь (часы стартуют с 08:00) |
| `market.ts:94` `seasonalityMult()` — цена электричества | `floor(h/24) % 360` | в 08:00 |
| `team.ts:22` `hiredDay` | `floor(h/24)+1` | в 08:00 |
| `Unreal/Rules/view.ts:160,167` (на `1f51843`) — тулбар и журнал в UE | `floor(h/24)+1`, время `floor(h%24)` | в 08:00; при старте показывает `00:00` вместо `08:00`. На `main@c511bd9` тулбар (`view.ts:196`) уже исправлен, журнал (`view.ts:211`) — нет |
| `src/ui/format.ts:16` `gameClock()` — браузер | `floor((h+8)/24)+1`, `(8+…)%24` | в полночь — правильно |

Следствие в UE: игрок видит «День 1», а контракт с `expiresDay = 3` (по `gameDay`) истекает раньше, чем он ожидает по тулбару; сводка бенчмарка «День N» не совпадает с часами. Сезонная надбавка включается в 08:00, хотя суточная граница экономики — полночь (в `advanceCompanySimulation` для этого есть отдельный `coolingBoundary`).

Исправление: один экспортируемый `gameClock(elapsed)` в `systems/` (не в `ui/`), использовать его в `view.ts`, `team.ts`, `seasonalityMult`. Убрать `coolingBoundary`, если сезон переключать на границе `gameDay`.

### L5. Бенчмарк не стареет — средняя (дизайн)

`competitor.ts:35,58`: для сравнения с конкурентом и «тормоза» его роста берётся `benchmark.last.total` без учёта возраста. Один тест на 80 GMI в день 5 навсегда даёт `COMPETITOR_GMI_DRAG` и выигрыш в сводках, даже если модель заменена квантованием… (там сбрасывается только через `benchmarkQuantization`). Логично добавить `BENCHMARK_VALID_DAYS` (например, 30) и после него использовать `iq * 0.8`, как для отсутствующего теста — это и стимул тратить 100 000 $ на повторные тесты.

### L6. Официальный контракт без срока выполнения — средняя (дизайн)

`contracts.ts:38-40` комментарий признаёт: обязательство «следующее обучение на официальных данных» ждёт бесконечно. Игрок берёт 60 000 $, никогда не обучает — штрафа нет, только блок новых предложений. Предложение: дедлайн `CONTRACT_TRAINING_DEADLINE_DAYS` (10–15), при просрочке — `fulfilled = false`, `CONTRACT_BREACH_REPUTATION`, возврат части выплаты.

### L7. Пожар сжигает «первый» сервер и стойку — низкая

`events.ts:117-119`: `victim.installedServers.slice(1)` — удаляется элемент с индексом 0 (не случайный, может быть резервный без `gridPosition`), и **стойка исчезает вместе с чипом**, тогда как штатный отказ (`equipment.ts:15-25`) стойку сохраняет. Использовать `failEquipment(state, victim.id, randomServer.id, 'Пожар…')` — одна механика, одно поведение.

### L8. Магазин чипов обещает мгновенную установку — низкая

`city.ts:11`: «магазин доставит и установит сервер сразу». Реально `CityCard.tsx:53` оформляет обычный заказ чипа на склад с доставкой 6–12 ч, а установка требует совместимой стойки. Текст нужно привести к поведению.

### L9. Фазы цен чипов — низкая

`market.ts:81`: `accelerator` (17 дней) и `flagship` (21 день) получают одинаковую фазу `π`; комментарий в `config.ts:84` обещает, что рынки «не двигаются синхронно». Вынести фазу в `CHIP_PRICE_PERIOD_DAYS` как объект `{ period, phase }`.

### L10. Мелочи

- `market.ts:299` `void rng` — параметр `rng` в `dailyInvestors` не используется; `procurement.ts:187` `_rng` тоже. Убрать из сигнатур, иначе создаётся впечатление стохастики.

## 4. Кодовые ошибки и качество кода

### C1. Три UI-системы в UE, две мёртвые

`AMaiPlayerController::BeginPlay` создаёт только `UMaiNativeWidget`. Поля `Screen` (`UMaiHUDWidget`) и `Flow` (`UMaiFlowWidget`) в `MaiPlayerController.h:33-34` никогда не инициализируются; `PlayerTick` каждый кадр проверяет `if (Screen)` впустую. Удалить или перенести в `Editor`-модуль как тестовую утилиту.

### C2. Дублирование правил в C++

`MaiSimulation.cpp` (404 строки) — самостоятельная экономика: `Economy()` считает доход как `users × 1.6` без цены токена/личности/квантования, `DailyStep()` — свой дрейф пользователей и свой суд, свои аукцион и АЭС. Всё это каждый тик **перезаписывается** проекцией из JS (`MaiRulesSubsystem::Project`), а `Validate()` может **отвергнуть** легитимное состояние браузера (лимиты `arrives ≤ now+48h`, `usersMicro ≤ 1e14`, `MoneyLimit`). Два источника правды — постоянный риск расхождений и лишний код на поддержку. Решение: оставить в C++ только то, чего нет в TS (ревью датасетов, сложности, концовки, прологи), а `mai::Simulation` свести к read-only структуре «снимок для UI/мира».

### C3. Плотность кода в UE

`MaiNativeWidget.cpp`, `MaiRulesSubsystem.cpp`, `MaiRulesPresentation.cpp`, `view.ts` написаны строками по 300–600 символов с несколькими операторами. Это делает ревью и отладку крайне дорогими. Добавить `.clang-format` и `prettier`/`eslint` с `max-len`, отформатировать один раз.

## 6. UI: как упростить и сделать «как в играх»

### 6.1 Диагноз

UE-интерфейс — это `view.ts` → JSON-узлы 11 типов → `UMaiNativeWidget::BuildNode`, где `button` = `UButton` с `FSlateRoundedBoxBrush(8)` + `UTextBlock` шрифтом `FCoreStyle Regular 14` (Roboto), `card` = `UBorder` с паддингом 16, вся раскладка — `UVerticalBox`/`UWrapBox`. Тулбар — `WrapBox` из 13 одинаковых кнопок с текстом. Отсюда ощущение «инструмент разработчика 2000-х»: нет иконографии, нет иерархии типографики (только 14/24), нет состояний и анимаций, нет «диегетических» элементов, много текста-инструкций внутри игрового экрана.

Браузерная версия лучше (есть иконки, карточки у зданий, тосты), но тоже перегружена подписями `card-note` 10 px и длинными абзацами.

### 6.2 Принципы, которые дадут 80 % результата

1. **Зоны HUD фиксированы, контент меняется.** Верх-лево: капитал / прибыль-час / пользователи (три KPI с иконками и цветной дельтой). Верх-право: часы + пауза/1×/3× (одна группа-«пилюля»). Низ: 5–6 иконок-вкладок (Город, Обучение, GMI, Каталог, Модели, Офис) с подписью 11 px под иконкой. Право: контекстная панель выбранного объекта (здание, ячейка, модель). Всё остальное — модальные окна по запросу.
2. **Прогрессивное раскрытие.** На экране только то, что можно сделать *сейчас*. Пояснение — в тултипе при наведении (задержка 400 мс), а не абзацем на экране. Пример: вместо «Официальные и неофициальные данные имеют разное происхождение и риск заражения.» — иконка ⓘ у кнопки.
3. **Числа как в стратегиях.** Крупная цифра (18–24 px, табличные цифры), единица мелко, дельта стрелкой и цветом (`+1 240 $/ч` зелёным). «Эффективная мощность 2.40» — техническая величина, игроку показывать «Вычисления: 2.4 ▲».
4. **Иконка + цвет вместо слова.** Состояния зданий: серый (не куплено), мятный (куплено), янтарный (троттлинг), красный (отказ). Каналы поставки: значок щита (официал) / значок маски (серый).
5. **Отзывчивость.** Hover 80–120 мс (яркость +8 %), нажатие — scale 0.97, панели выезжают за 180–220 мс с ease-out, тосты — снизу-по-центру 3 с. Звуки клика/покупки/ошибки (3–4 коротких сэмпла) резко повышают ощущение «игры».
6. **Один набор токенов дизайна** для браузера и UE:

```
Цвета:   bg0 #0b1418  bg1 #10201f  bg2 #17302d  border #2a4a45
         text #e6efec  muted #8fb0a8  accent #59d6a8  accent2 #7bb7ff
         warn #f2b45f  danger #ef6b6b
Шрифт:   Inter / Manrope (UI), JetBrains Mono или Inter Tabular (цифры)
Размеры: 11 / 13 / 15 / 18 / 24 / 32
Отступы: 4 / 8 / 12 / 16 / 24 / 32;  радиусы 6 / 10 / 16
```

### 6.3 Конкретный план для UE

1. **Не отказываться от JSON-view**, это хорошая архитектура (UI — чистая функция состояния). Расширить словарь узлов: `kpi {icon,label,value,delta}`, `tabs`, `icon-button`, `badge`, `stat-row`, `grid {cols}`, `divider`, `tooltip`. Убрать из `view.ts` длинные `text(...)`-инструкции в поле `hint` у кнопок.
2. **Стили из одного места.** Создать `UMaiStyleAsset` (DataAsset) с цветами, шрифтами (`UFont` из TTF Inter/Manrope в `Content/UI/Fonts`), кистями 9-slice (`FSlateBrush` с `Margin`) для панели/кнопки/карточки. `BuildNode` берёт кисти оттуда, а не из `FCoreStyle`.
3. **Кнопки.** Четыре роли: `primary` (заливка accent, тёмный текст, иконка слева), `secondary` (обводка 1 px, прозрачная заливка), `ghost` (только текст, для «Закрыть»), `danger`. Состояния Normal/Hover/Pressed/Disabled с разными кистями, `UButton::SetStyle` один раз при создании. Иконки — SVG из Lucide/Phosphor, конвертированные в 64 px PNG-атлас; рядом с текстом через `UHorizontalBox`.
4. **Тулбар.** Заменить 13 текстовых кнопок на: логотип-кнопка «в город» · KPI×3 · часы+скорость · 6 иконок-вкладок · иконки «журнал/сохранить/настройки». Ширина фиксирована, всё влезает в 1280 px без переносов (сейчас `WrapBox` переносит строки).
5. **Маркеры на карте.** Сейчас это те же кнопки с текстом над зданием (`BuildMapMarkers`). Сделать «пин»: круг 28 px с иконкой типа здания + цветной ободок статуса, подпись появляется при наведении или при зуме ближе порога. Выбранный — увеличенный пин + контекстная карточка справа.
6. **Модальные окна.** Заголовок 24 px + подзаголовок muted + контент + футер с кнопками справа. Закрытие по Esc и клику по затемнению (сейчас только кнопка «Закрыть»).
7. **Шрифты и масштаб.** Убрать `FCoreStyle::GetDefaultFontStyle`; `UIScaleCurve` уже настроен — этого достаточно, но нужно проверить кириллицу в выбранном TTF.
8. Если хочется быстрее — плагин **Common UI** (`CommonButtonBase`, `CommonActivatableWidgetStack`) даёт стек экранов, фокус и стили из коробки; `UMaiNativeWidget` может создавать `CommonButtonBase` вместо `UButton`.

### 6.4 План для браузера

- Те же токены в `:root` (`styles.css`), сейчас цвета разбросаны хексами по 349 строкам.

## 7. Карта: детализация без ущерба производительности

### 7.1 Что есть сейчас

| | Браузер | UE |
|---|---|---|
| Геометрия | `living-city.glb` 1.6 МБ, 37 батчей, 12 интерактивных объектов, 106 инстансов актёров | 29 395 инстансов, 216 уникальных мешей, 195 с 3 LOD, 1 695 HISM |
| Свет | 1 направленный + hemisphere, 6 точечных ламп ночью, одна теневая карта 2048 | Sun + SkyLight + Lumen GI/Reflections + VSM, авто-экспозиция, эмиссия окон по времени |
| Камера | Орто, зум 0.65–22 | Перспектива 65°, орбита |
| Атмосфера | `THREE.Fog`, смена цвета неба по часам | Exposure bias −1.2 EV на общем виде |
| Жизнь | Машины/люди/собаки по маршрутам, 30 Гц, редкая машина | Нет |

Автор сам отмечает: «дальняя карта бледная», дата-центры — кубы (`build_city_content.py:220-226` использует `/Engine/BasicShapes/Cube`).

### 7.2 Правило: красота = свет + вариативность + жизнь, а не полигоны

**1. Освещение и пост-обработка (почти бесплатно, даёт больше всего).**
- Солнце под 35–50° к горизонту с тёплым цветом (`#ffe8c8`) и холодным небом (`#9fb8d8`) — длинные тени рисуют объём города. Сейчас в UE солнце крутится по часам, но контраст тёплого/холодного слабый.
- Вместо Lumen: SkyLight с захваченной кубмапой + **Distance Field AO** (или SSAO) — затемнение в узких дворах и у оснований зданий делает 70 % «дорогого» вида.
- Цветокоррекция через **LUT** (одна текстура 256×16): слегка приподнятые тени, тёплые света, насыщенность +10 %. Это лечит «бледную даль».
- Bloom только на эмиссивных окнах/вывесках (порог 1.0), лёгкая виньетка 0.2, никаких lens flare (уже выключены).
- **Exponential Height Fog** с цветом, взятым из неба, плюс `Volumetric Fog = off` (дорого) — глубина кадра без затрат.

**2. Микродетали через материалы, а не геометрию.**
- Trim-sheet/атлас 2K на все фасады: окна, карнизы, вентрешётки как текстура с normal map. Один материал — сотни зданий.
- **Detail normal** (тайлинг 0.1 м) бетона/штукатурки — крупным планом даёт шершавость, вдали исчезает.
- Вариативность цвета фасадов через **PerInstanceRandom** в материале (UE: `PerInstanceRandom` нода; three.js: `instanceColor`). Одинаковые дома перестают выглядеть копиями.
- Грязь/разметка/лужи — **Decal-ы** (UE DBuffer decals дешёвые в deferred) или вторичный UV-слой с масками.

**3. Плотность через инстансинг реквизита.**
Добавить 20–30 мелких мешей (кондиционеры на крышах, антенны, баки, скамейки, фонари, кусты, припаркованные машины, вывески, бордюры, деревья 2–3 вида) и рассыпать их **тысячами** инстансов. При HISM/Nanite цена — доли миллисекунды. Именно реквизит на крышах и улицах даёт ощущение «живого» города при виде сверху.

**4. Nanite для статики.** Все здания, дороги, реквизит — Nanite. Это снимает вопрос LOD-переходов (сейчас 21 меш без LOD), уменьшает draw calls до единиц и делает VSM быстрым. Non-Nanite оставить только для растительности с WPO (ветер) и масок; для дальних деревьев — **impostor-billboard** (плагин ImpostorBaker) вместо `SetCullDistances(60000,80000)`, который просто убирает лес.

**5. Свет ночью без point-light.** Окна — эмиссия по маске (уже есть), фонари — эмиссивный конус (плоский меш с аддитивным материалом) + одна общая «лужа света» декалью. В three.js каждый `PointLight` увеличивает стоимость **всех** фрагментов (forward-рендер) — 6 сейчас терпимо, больше не делать. В UE точечные светильники без теней дешевы, но их всё равно не должно быть сотни.

**6. Жизнь.** В браузере уже есть `StreetLife` — перенести идею в UE: машины/люди как `UInstancedStaticMeshComponent` с обновлением трансформов 20–30 Гц из одного C++ актёра (аналог `StreetLife.update`), либо Niagara с mesh-renderer по сплайнам дорог. Плюс: мигающие огни антенн (эмиссия × `sin(time)`), дым из труб (2–3 Niagara-спрайта), птицы (Niagara, 20 частиц), рябь воды (панорамируемый normal map). Всё это <0.3 мс.

**7. Композиция камеры.** Угол 55–65°, лёгкий DoF на краях (UE `DepthOfFieldFstop` 4–8 при общем виде, off вблизи) — эффект «макета города», который любят в градостроительных играх и который маскирует бедность дальних планов. Ограничить границы камеры так, чтобы край мира не попадал в кадр (в браузере `bounds` уже есть).

**8. Дата-центры.** Заменить кубы на 3–4 модульных меша (корпус, чиллер, трансформатор, забор) и собрать площадки инстансами тех же мешей — и дёшево, и узнаваемо.

### 7.3 Бюджет и как измерять

Целевая машина — «средний ПК» (GTX 1060 / RX 580, 4 ядра), 1080p, 60 FPS:

| Метрика | Цель | Как смотреть |
|---|---|---|
| Видимые треугольники | ≤ 2 М (с Nanite — не критично) | `stat RHI`, `stat Nanite` |
| Draw calls | ≤ 600 | `stat SceneRendering` |
| Теневые источники | 1 (солнце) | `stat ShadowRendering` |
| GPU-кадр | ≤ 12 мс | `stat GPU`, `ProfileGPU` |
| Game-thread | ≤ 6 мс (сейчас QuickJS-обмены каждые 250 мс) | `stat Game`, Unreal Insights |
| Память текстур | ≤ 1.5 ГБ | `stat Streaming` |

В браузере: `renderer.info.render.calls` уже пишется в `dataset`, добавить `three` `Stats` в DEV и целиться в ≤ 150 draw calls, ≤ 600 К треугольников, ≤ 2 МБ геометрии после Draco.

## 8. Общий анализ проекта

### 8.1 Сильные стороны

- **Ядро правил** — чистые функции с явными `ActionResult`, детерминированный RNG, тесты на регрессии экономики, «золотые» состояния по SHA-256. Это редкость для инди-проекта и главный актив.
- **Сохранения** валидируются до применения, с откатом, версионированием V0→V3 и миграциями; в UE — атомарная запись с контрольной суммой и бэкапом.
- **Паритет** браузер ↔ UE обеспечен исполнением одного и того же кода, а не переписыванием.
- **Честная документация**: отчёты явно отделяют «проверено» от «не проверено».

### 8.2 Слабые стороны и риски

1. **Архитектурная сложность порта.** Три слоя состояния (zustand-store в QuickJS → JSON → `mai::Simulation` зеркало → `mai::Campaign`), синхронизируемые каждые 250 мс с валидацией и откатами. Любая новая фича требует правок в TS-правилах, `view.ts`, `MaiRulesSubsystem::Project`, `Campaign` и `Validate`. Это главный тормоз развития.
2. **Три UI-реализации** и graybox-мир в кодовой базе одновременно.
3. **Баланс не проходил human playtest** (отмечено в ADR): стартовые 12 000 $ при гараже 1 500 $ + комплект 4 800 $ дают минимум 1 192 $ до первого дохода на 64-м часу (по тестам) — узкий коридор; серый контракт и вечный ад-буст ломают экономику в другую сторону.
4. **Производительность на слабом железе неизвестна**, а конфиг рендера выставлен на максимум (Lumen/VSM).
5. **Бинарные ассеты в git** без LFS.
6. **Смешение языков** в коде и строках, отсутствие таблицы локализации.
7. Документация и отчёты (≈20 файлов) требуют поддержки; часть уже устарела относительно кода (`Unreal/MakeYourAI/README.md` описывает graybox-запуск, `UNREAL_MIGRATION.md` — статус `SOURCE_SCAFFOLD`, при том что релиз 0.0.1 уже упакован).

### 8.3 Приоритеты

**P0 — исправить до следующего релиза**
- L1 ад-буст, L2 серый контракт, L3 бухгалтерия найма, L4 единый календарь. Добавить тесты на каждое.
- U1: выключить Lumen/VSM по умолчанию (или включить Nanite + пресеты качества).

**P1 — ближайшие итерации**
- Удалить мёртвые UI/graybox (C1), сократить `mai::Simulation` до снимка (C2).
- U3/U4: снизить частоту и объём обменов с QuickJS.
- U2: перегруппировать HISM по мешу.
- UI: токены дизайна + иконки + KPI-панель (раздел 6.3, пункты 1–5).
- Сжать PNG превью, селекторы в `App.tsx`.

**P2 — качество и масштаб**
- Nanite + реквизит + LUT/AO/фог (раздел 7).
- Git LFS, `.clang-format`/`prettier`.
- Таблица строк RU/EN, единая локаль.
- Автобенчмарк железа при первом запуске, меню качества.
- Human playtest 2–3 партии с логом решений — сверить с таблицей ADR §12.

### 8.4 Что я не смог проверить

- Сборку и запуск UE (нет движка) — все выводы по C++ статические, но подтверждены чтением кода и конфигов.
- Визуальный результат Blender-экспорта и пайплайна `Unreal/Tools`.
- Реальную частоту кадров на слабом железе — только по отчёту автора (RTX 3090, 50 % GPU).
